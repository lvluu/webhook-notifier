# Benchmarks

This directory contains the benchmark harness, the reusable HTTP receiver fixture, the shared benchmark profiles, and the committed scenario reports.

## Contents

- `receiver/` - configurable HTTP test server used by the scenarios and integration tests.
- `scenarios/` - the five benchmark drivers invoked by `cmd/bench`.
- `profiles.yaml` - shared `dev` and `stress` benchmark profiles.
- `results/` - committed markdown reports generated by the scenario runs.

## Running A Scenario

Each scenario is launched through the benchmark command:

```bash
BENCH_PROFILE=stress go run ./cmd/bench scenario1
BENCH_PROFILE=stress go run ./cmd/bench scenario2
BENCH_PROFILE=stress go run ./cmd/bench scenario3
BENCH_PROFILE=stress go run ./cmd/bench scenario4
BENCH_PROFILE=stress go run ./cmd/bench scenario5
```

Use `BENCH_PROFILE=dev` for the smaller, faster tuning profile while iterating locally.

If you prefer `just`, the repo exposes bench recipes in `justfile`.

## Profiles

All scenarios read from the same YAML file:

- `dev` - minimal settings for fast iteration.
- `stress` - larger settings for benchmark runs and report generation.

The shared schema keeps the run shape consistent across scenarios while still allowing each one to tune its own worker counts, delivery counts, and breaker settings.

Breaker handling:

- Scenarios 1-4 use `breaker_failure_threshold: 0`, which disables breaker tripping entirely.
- Scenario 5 uses a real threshold and is the dedicated dead-partner / breaker-protection benchmark.

## Database Isolation

Bench runs start their own Postgres testcontainer by default and apply the repo migrations automatically.

Useful overrides:

- `BENCH_DATABASE_URL` - point the benchmark at an existing database instead of starting a container.
- `BENCH_KEEP_DATABASE=1` - keep the benchmark container alive after the run.
- `BENCH_DATABASE_INFO_FILE=/path/to/file` - write the live connection string somewhere explicit.

When no path is provided, the benchmark writes the connection string to `/tmp/bench-postgres.dsn` so you can inspect the database while the scenario is running.

## Scenario Map

- `scenario1` - fairness under load with a late-arriving small customer.
- `scenario2` - transient and recovering partner failures.
- `scenario3` - terminal 4xx fast-fail behavior.
- `scenario4` - horizontal scale, claim atomicity, and idempotency stability.
- `scenario5` - dead-partner circuit breaker and healthy-customer pool protection.

## Reports

Each run rewrites a markdown report under `bench/results/`.

Current reports:

- `bench/results/scenario-1.md`
- `bench/results/scenario-2.md`
- `bench/results/scenario-3.md`
- `bench/results/scenario-4.md`
- `bench/results/scenario-5.md`

These reports are intended to be committed so the benchmark results stay reviewable and comparable across revisions.
